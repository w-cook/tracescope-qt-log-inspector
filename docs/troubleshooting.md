# Troubleshooting TraceScope

Use this guide when TraceScope behaves differently from what you expected. Start with the symptom, check the likely cause, and follow the linked guide when you need the complete workflow. A problem that looks like missing evidence can sometimes be a filter, an import mapping, or a source that has changed since it was first opened.

**Important:** Before experimenting with **Reload**, replacing a source file, or changing an investigation's backing mode, save work that you need to keep. If the original log may be truncated, rotated, or deleted, preserve currently admitted evidence and [understand what your workspace actually saves](saving-and-restoring.md#1-understand-what-tracescope-saves). Do not modify an important original log simply to test an import.

## Before you change anything

These checks help distinguish a presentation or configuration problem from missing source records:

1. **Identify what you are looking at.** Is the active workspace document an investigation or an existing comparison? For an investigation, check its backing mode and source information in its tab and tooltip.
2. **Check the current scope.** Look at the Event Table's record counts and active filters before concluding that records are missing. Analytical views and the Event Table do not always use identical populations.
3. **Use a representative source record.** If the issue starts at import, compare a row in **Source Record Preview** with **Selected Raw Source**, then look at **Validation** and import diagnostics.
4. **Preserve evidence before testing recovery.** Save a complete workspace for annotations and working context. If you need the current evidence to become independent of a changing external log, consider **Source > Preserve as Snapshot Only...** and then save the workspace. A standalone `.tsinv` captures evidence but not the full annotated workspace.

See [Saving and Restoring](saving-and-restoring.md) for the distinctions among SourceBacked, SnapshotBacked, Hybrid, workspace saves, and standalone snapshots.

## 1. Launch and interface problems

| Situation | What to check |
| --- | --- |
| The Windows application will not start from the downloaded package. | Extract the **entire** Windows x64 archive before launching `TraceScope.exe`. Keep its packaged companion files and directories together rather than moving only the executable. Check that you downloaded an appropriate package from [Releases](https://github.com/w-cook/tracescope-qt-log-inspector/releases). See [Getting Started: Windows](getting-started.md#windows) for more information. |
| The Linux AppImage does not launch when invoked directly. | Confirm that you downloaded the Linux x86_64 package and made the actual AppImage executable (`chmod +x`), then run it from a terminal to inspect any startup message. Do not assume that Windows ZIP instructions apply to the AppImage. See [Getting Started: Linux](getting-started.md#linux) for more information. |
| A bundled sample or its profile is missing. | In the Windows package, look under the included `samples/` folder. On Linux, obtain the separate release samples archive or the repository samples. Confirm that the **source log** and its **matching profile** are two different files. See [Getting Started: Find the example](getting-started.md#2-find-the-example-log-and-its-profile) and [Supported Formats: Bundled examples](supported-formats.md#4-bundled-format-examples). |
| Import Configuration does not look like the documentation screenshot. | Its layout changes with available width and interface scale. A wide layout has side-by-side profile and preview areas; a compact layout has **Profile & Mappings** and **Source Preview** tabs. Resize the dialog or use **View > Interface Scale** from the main window. See [Importing Logs: Find your way around Import Configuration](importing-logs.md#2-find-your-way-around-import-configuration). |
| An investigation panel, tab, or control appears to be missing. | Check for a collapsed section, a constrained-height layout, or a different active workspace document. Expand the section's chevron, enlarge the window, or adjust **View > Interface Scale**. Some analytical controls also depend on fields actually supplied by the imported data. See [Investigating Logs: Common investigation pitfalls](investigating-logs.md#12-common-investigation-pitfalls). |

## 2. Import and profile problems

**Start here:** Import Configuration separates a *structurally valid profile* from a *correct interpretation of this particular file*. Passing **Validation** does not prove that every field path, timestamp, or regex capture matches the source. Use preview and diagnostics before changing several settings at once.

| Situation | What to check |
| --- | --- |
| No format is suggested, or a `.log`/`.txt` file is given the wrong suggestion. | Those extensions do not identify a unique log layout. Inspect the source content and select the correct **Format**, use an appropriate recognized preset, or load an existing profile. See [Supported Formats: Format suggestions](supported-formats.md#2-format-suggestions-and-file-extensions). |
| Import opens no records, or JSON/XML selects the wrong content. | Confirm that you chose **JSON Lines** for independent JSON records on separate lines versus **Structured JSON** for a complete document. For nested Structured JSON/XML, set **Record path** to the location of the repeated records. Field paths are relative to each selected record. See [Supported Formats: Format-specific requirements](supported-formats.md#3-format-specific-requirements) and [Import Profiles: Source paths](import-profiles.md#3-source-paths-and-format-specific-configuration). |
| The preview contains records, but important columns are blank or show unexpected data. | Select a representative preview row and compare mapped values with **Selected Raw Source**. Check exact source-path spelling, nested paths, and the six optional canonical field mappings. Leave truly absent canonical fields blank instead of manufacturing them. See [Import Profiles: The six canonical fields](import-profiles.md#the-six-canonical-fields). |
| Severity is unavailable or failures have the wrong severity. | Verify the **Severity** source path *and* its **Severity Aliases**. A source label such as `FAIL` needs a mapping that reflects its meaning; an incorrect alias can materially affect filtering and analysis. See [Import Profiles: Severity aliases](import-profiles.md#severity-aliases). |
| Timestamps are missing, invalid, or unexpectedly offset. | Check the actual source text, the **Timestamp** field path, the type and order of **Timestamp Rules**, and the source's timezone. RFC 3164 lacks a year and timezone, so its year is inferred relative to import context and its times are interpreted using the local timezone; inspect the associated diagnostic. See [Import Profiles: Timestamp rules](import-profiles.md#timestamp-rules) and [Supported Formats: Syslog](supported-formats.md#syslog-rfc-5424-and-rfc-3164). |
| A custom attribute is visible in raw source but absent from the investigation. | Verify its source path or add an explicit named mapping. When appropriate, enable **Preserve unmapped source fields**. Auto-detection uses a limited preview and might not discover attributes appearing only in later records. Syslog RFC 5424 parameters require the correct structured-data ID and nested path. See [Import Profiles: Custom fields and unmapped data](import-profiles.md#5-custom-fields-and-unmapped-data). |
| A regex-based import skips lines or captures the wrong text. | Check the pattern against several ordinary and unusual lines, confirm the required **named capture groups**, and inspect the import's skipped-record count and diagnostics. A valid regex can still fail to describe the actual log. See [Import Profiles: Regex Plain Text](import-profiles.md#regex-plain-text-named-captures-become-source-fields). |
| CSV/TSV columns are wrong, or rows are skipped. | Verify the correct importer and delimiter, header names, and input quoting. The supported CSV/TSV importers do not treat quoted fields spanning multiple physical lines as one record. See [Supported Formats: CSV and TSV](supported-formats.md#csv-and-tsv). |
| The profile cannot be loaded or saved. | Verify that it is a valid version-1 TraceScope profile with the required JSON properties and a supported importer. Fix any **Validation** errors before saving. Use **New From Source** cautiously: it replaces the current working profile configuration after confirmation when you have edited it. See [Import Profiles: Saved profile JSON reference](import-profiles.md#6-saved-profile-json-reference) and [Importing Logs: Save, load, and reset profiles](importing-logs.md#4-save-load-and-reset-profiles). |
| A large Structured JSON/XML file does not preview automatically. | For structured files above the 16 MiB automatic-preview threshold, use **Refresh Preview** to run the explicit preview. The ordinary preview is limited to the first 50 *processed* records, so also inspect full-import diagnostics when errors occur later in a file. See [Importing Logs: Verify the preview](importing-logs.md#5-verify-the-preview-and-validation) and [Import large files](importing-logs.md#7-import-large-files). |
| Expected rotated log files were not included. | Select the active file and review **Include rotations** / **Review...**. Verify the detected filenames, ordering, and whether the files actually belong to the same source family. Do not confuse separate rotated physical files with generations caused by same-path truncation or replacement. See [Importing Logs: Import a rotated source family](importing-logs.md#6-import-a-rotated-source-family). |
| Windows event files are rejected. | The XML importer accepts supported **Windows Event XML** records and collections, not native binary `.evtx` files. Export or obtain XML-formatted event records and use an appropriate profile. See [Supported Formats: Structured XML](supported-formats.md#structured-xml-including-windows-event-xml). |

**Isolate a source-specific problem:** Try a bundled sample with its *matching* supplied profile. If that works, return to the original source and check its format, data variation, and profile. A working sample does not establish that an unrelated production log has the same layout.

## 3. Filtering, navigation, and analysis problems

| Situation | What to check |
| --- | --- |
| An imported investigation's Event Table appears empty. | Check every active filter, not only Severity. **Reset Filters** and then reapply conditions one by one. If the unfiltered investigation is also empty, return to its import result and profile. See [Investigating Logs: Understand what filtering changes](investigating-logs.md#2-understand-what-filtering-changes). |
| A record is visible in the source but does not match a custom-field or time filter. | Check the imported field's exact name and value in **Event Details**. For time filters, check the **UTC** boundaries and whether that record actually has a usable timestamp. Source records lacking a filtered field may not match that filter. See [Investigating Logs: Custom attributes](investigating-logs.md#5-filter-using-source-specific-custom-attributes) and [Focus on a time window](investigating-logs.md#7-focus-on-a-time-window). |
| The timeline, Issue Summary, or Analytics count disagrees with the Event Table. | Distinguish the complete imported population, **visible** filtered rows, and the **analysis** population. Analytical views honor source-data filters but ignore review-only **Bookmarks only** and **Finding status** filters. Clear or compare those review filters before treating a count difference as an error. See [Investigating Logs: Understand what filtering changes](investigating-logs.md#2-understand-what-filtering-changes). |
| Issue Summary or an analytical section is absent or unavailable. | Its required source information might not be mapped or populated. For example, Issue Summary needs usable severity and subsystem data, while time-based charts and bursts need usable timestamps. Recheck the source and mappings rather than filling absent canonical fields with invented data. See [Investigating Logs: Issue Summary](investigating-logs.md#9-use-issue-summary-as-another-entry-point) and [Analytics](investigating-logs.md#10-explore-frequencies-and-detected-bursts). |
| Next/Previous or surrounding-event navigation does not show the source lines you expected. | Navigation follows the currently visible records and sort order. Narrow filters may hide intervening records. Widen or reset filters, then apply an appropriate chronological sort before investigating neighboring evidence. See [Investigating Logs: Follow records using navigation and sorting](investigating-logs.md#6-follow-records-using-navigation-and-sorting). |
| The timeline is cramped, or drilling into a bar changes several filters. | Try **Auto** or a broader **Bucket size** and scroll horizontally if needed. A bar double-click applies its time bucket as an investigation filter and may also select its severity or subsystem; inspect the active filters afterward. See [Investigating Logs: Explore the event timeline](investigating-logs.md#8-explore-the-event-timeline). |
| Detected Bursts changes after drilling into a burst, or no burst appears. | Burst detection reruns against the *new* source-data-filtered population. **Auto** may recalculate timing settings from that narrower population; **Manual** fixes those settings but not the input population. **Reset Filters** to revisit the original results. No detected burst is not proof that no incident occurred. See [Investigating Logs: Bursts](investigating-logs.md#bursts-concentrated-elevated-activity). |

## 4. Findings and annotations

| Situation | What to check |
| --- | --- |
| A bookmarked or noted record does not appear in **Findings**. | A bookmark or note alone does not classify a finding. Set its **Finding status** to **Open**, **Resolved**, or **Dismissed**. See [Findings: Create an Open finding](findings.md#3-create-an-open-finding). |
| A finding appears in Findings but not the current Event Table. | Findings covers explicitly classified records independently of current Event Table filters. Select it for a preview; use its reveal action to locate the record and adjust filters as needed. See [Findings: Navigate between Findings and the Event Table](findings.md#5-navigate-between-findings-and-the-event-table). |
| A finding has no description, or edited notes are not reflected in its list entry. | Select the intended record, **Add Note** or edit the existing note in **Event Details**, and save the note. Confirm you have the correct record selected before editing. See [Findings: Add and revise an analyst note](findings.md#4-add-and-revise-an-analyst-note). |
| An export contains fewer findings or bookmarked findings than expected. | **Filtered Findings** follows active Event Table filters, **All Findings** includes every classified finding, and **Bookmarked Findings** requires *both* a bookmark and a finding classification. See [Findings: Export the findings you need](findings.md#7-export-the-findings-you-need). |

## 5. Live-follow and source-change problems

**First distinction:** **Following** describes ingestion state; **Follow Newest** controls where the Event Table stays positioned. One can work without the other.

| Situation | What to check |
| --- | --- |
| Live-follow controls are unavailable or the source will not start following. | Check that the investigation has an accessible, connected external source and a live-capable importer/profile. A standalone SnapshotBacked investigation has no active source to follow until a valid reconnection is established. For live structured documents, check their required repeating-record structure. See [Live Following: Understand what Live Following does](live-following.md#1-understand-what-live-following-does) and [Supported Formats: Live compatibility](supported-formats.md#5-live-following-compatibility). |
| Following remains **Stopped**, or the status changes to **Error**. | Confirm that the producer's **active file** still exists at the configured path and is readable. Hover over the error status for its message. If the source was moved, use the explicit source-path/reconnection workflow; do not silently substitute an unrelated file. See [Live Following: Start following the generated file](live-following.md#3-start-following-the-generated-file) and [Saving and Restoring: Reload, relocate, and resume](saving-and-restoring.md#6-reload-relocate-and-resume-work-deliberately). |
| Status says **Following**, but no new records appear. | Check that the producer is writing to the *same active path*, has written a complete supported record, and that your filters permit the new record to appear. A partially written line or structured element may remain pending until complete. See [Live Following: Incomplete writes](live-following.md#incomplete-writes). |
| New records are arriving, but the table does not automatically scroll. | Check **Follow Newest** separately from following status, plus active sort and filters. Disabling Follow Newest lets you inspect older records without stopping ingestion. See [Live Following: Use the live controls](live-following.md#4-use-the-live-controls-deliberately). |
| Resume fails to recover records written while paused. | Determine whether the producer truncated, replaced, or rotated the source while reading was paused. TraceScope can catch up only on unread bytes that still exist. Use a saved evidence snapshot/workspace to preserve records *already admitted*; neither can reconstruct bytes never read. See [Live Following: File changes](live-following.md#6-understand-file-changes-during-live-following). |
| You need earlier rotated files as well as the active followed file. | Review **Include rotations** when importing the active source and verify the physical source-family selection. Rotated files remain distinct physical files within the logical source family; truncation or same-path replacement is tracked through source generations. See [Importing Logs: Rotated source family](importing-logs.md#6-import-a-rotated-source-family) and [Live Following: Rotated source families](live-following.md#rotated-source-families). |
| The optional live-generator example ends too quickly or writes to the wrong file. | Check the launcher **Scenario**, **Output**, **Format**, speed, and looping settings. The generator writes an ordinary external file; TraceScope must import and follow that exact generated output using the matching profile. Use a *disposable* path because some scenarios intentionally truncate, replace, or rotate it. See [Live Following: Prepare the generator](live-following.md#2-optional-prepare-the-live-log-generator-walkthrough) and [Live-Log Generator](live-log-generator.md). |

## 6. Saving, reopening, and source recovery

**Do not treat all saves as interchangeable.** A `.tsw` plus its matching `.sessions/` folder preserves the working investigation context; a standalone `.tsinv` preserves evidence from one investigation at a point in time. Neither makes deleted, never-admitted source bytes recoverable.

| Situation | What to check |
| --- | --- |
| A moved or copied workspace opens with missing investigations or evidence. | Keep `name.tsw` and the matching `name.sessions/` folder **together**. A SourceBacked investigation may also need access to its external source. Do not rename or manually rearrange the companion snapshot files. See [Saving and Restoring: The two parts of a saved workspace](saving-and-restoring.md#the-two-parts-of-a-saved-workspace). |
| Opening a workspace reports **Workspace Source File Missing**. | If the original source was moved, use **Locate File...** and choose the correct source. If the source is unavailable but the workspace has usable saved evidence, use **Open Saved Snapshot** to restore it as SnapshotBacked. **Skip Session** skips that investigation for this opening attempt; **Cancel** abandons the opening. See [Saving and Restoring: Recover a missing source](saving-and-restoring.md#3-optional-walkthrough-recover-when-the-original-source-is-missing). |
| **Open Saved Snapshot** is unavailable during recovery. | Check that the `.sessions/` folder was copied intact and contains readable snapshots. Recovery cannot manufacture a snapshot that was never saved or is no longer available. See [Saving and Restoring: The two parts of a saved workspace](saving-and-restoring.md#the-two-parts-of-a-saved-workspace). |
| Earlier live events disappear after reopening or reloading a saved workspace. | Check the investigation's **backing mode**. SourceBacked ordinarily reconstructs from the *current external source*; that file may have been truncated, replaced, or rotated since evidence was first admitted. Preserve important evidence as SnapshotBacked or use a deliberate Hybrid workflow when appropriate. See [Saving and Restoring: Understand the three backing modes](saving-and-restoring.md#5-understand-the-three-backing-modes). |
| Opening `.tsinv` shows records but not previous bookmarks, findings, filters, or layout. | This is expected for a standalone investigation snapshot: it stores evidence, not the broader workspace state. Reopen the full `.tsw` and companion `.sessions/` package to restore annotations and other workspace context. See [Saving and Restoring: Save or open an individual snapshot](saving-and-restoring.md#4-save-or-open-an-individual-investigation-snapshot). |
| A SnapshotBacked investigation cannot follow a source, or reconnection fails. | SnapshotBacked evidence has no active file until a suitable source can be reconnected. Verify the recorded source-continuity information and the candidate file's identity; source relocation is **not** permission to substitute a different log. See [Saving and Restoring: Reconnect preserved evidence](saving-and-restoring.md#reconnect-preserved-evidence-to-an-external-source). |
| You want a Hybrid investigation to return to ordinary source authority. | Understand what is being discarded as an authoritative baseline before choosing the explicit return-to-source operation. Do not use a reload or source transition merely to clear a visual symptom. Make a separate saved workspace copy if you need a reversible experiment. See [Saving and Restoring: Return a Hybrid investigation to source authority](saving-and-restoring.md#deliberately-return-a-hybrid-investigation-to-source-authority). |

## 7. Session-comparison problems

Existing comparison documents are *point-in-time snapshots* of the two complete imported investigations at comparison creation. Their values do not silently change when the original investigations receive new records or have their filters changed.

| Situation | What to check |
| --- | --- |
| A count difference has the opposite sign from what you expected. | Confirm which investigation was assigned **Baseline** and which **Comparison**. Every displayed delta means **Comparison − Baseline**. See [Comparing Sessions: Create the comparison](comparing-sessions.md#3-create-the-comparison). |
| Comparison counts do not match the investigations' current Event Tables. | Comparison uses the complete imported sessions at creation, **not** their current visible filters. Source investigations may have been filtered or changed since then. If you need a current comparison, create a new comparison document after choosing the intended complete investigations. See [Comparing Sessions: Investigate the differences](comparing-sessions.md#7-investigate-the-differences-in-the-original-sessions). |
| A comparison dimension is **Unavailable**, or a custom field does not appear. | Check whether both sources supplied usable values and exactly matching mapped **custom-field names**. Numeric custom-field summaries require finite numerical populations in both sessions; categorical comparisons intentionally omit some high-cardinality or unsuitable values. **Unavailable** is not the same as zero difference. See [Comparing Sessions: Key Differences](comparing-sessions.md#key-differences-look-for-changes-worth-investigating). |
| Burst Comparison is missing, **Unavailable**, or shows zero bursts. | Those mean different things: you did not enable burst comparison, the requested analysis lacks suitable settings/data, or valid detection found no bursts. The comparison uses one fixed shared configuration, unlike separately configured interactive burst views. See [Comparing Sessions: Interpret Burst Comparison](comparing-sessions.md#5-interpret-burst-comparison). |
| A saved comparison reopens without one of its original investigations. | Saved comparison documents remain independent of the source session objects that originally produced them. Their captured analysis stays viewable, but source-level event inspection requires the corresponding investigation evidence to be available. See [Comparing Sessions: Save or share](comparing-sessions.md#8-save-or-share-the-comparison) and [Saving and Restoring](saving-and-restoring.md). |

## 8. Export and report problems

| Situation | What to check |
| --- | --- |
| **Export Filtered Results...** is unavailable or exports fewer records than expected. | Activate the intended investigation document and verify the active filters and visible record count. This command exports the *complete current filtered population*, not just the table rows physically visible on screen. See [Reporting and Exporting: Export filtered records](reporting-and-export.md#3-export-the-currently-filtered-records-to-csv). |
| A classified or bookmarked record is absent from a findings CSV. | Check the selected findings-export scope. **All Findings**, **Filtered Findings**, and **Bookmarked Findings** use different inclusion rules; a bookmark alone is not an explicitly classified finding. See [Reporting and Exporting: Export findings](reporting-and-export.md#4-export-classified-findings-to-csv). |
| **Export...** is disabled in the HTML-report dialog. | Provide a nonempty report title and select at least one eligible investigation or comparison document under **Included Workspace Documents**. See [Reporting and Exporting: Configure the HTML report](reporting-and-export.md#6-configure-and-export-the-html-report). |
| Findings or evidence expected in an HTML report are absent. | Check the included source investigations, their current filters and annotations, and **Include supporting evidence records**. Extra burst-supporting records depend on that option, while annotated/bookmarked core evidence and explicitly classified findings have separate rules. See [Reporting and Exporting: Configure the HTML report](reporting-and-export.md#6-configure-and-export-the-html-report) and [Read and verify the report](reporting-and-export.md#7-read-and-verify-the-html-report). |
| The comparison section and an investigation section in the *same* HTML report appear to use different record scopes. | An existing comparison retains the full-session snapshot captured when it was created, while a source-investigation section reflects its state and filters at report creation. The export does not recalculate the comparison to match later filters. See [Reporting and Exporting: Review the included comparison](reporting-and-export.md#review-the-included-comparison). |
| The HTML report appears to lack sections, details, or supporting records when opened. | Many detail blocks start **collapsed** and some contain additional nested collapsible blocks. Expand the relevant sections before concluding the report omitted their contents. See [Reporting and Exporting: Read and verify the HTML report](reporting-and-export.md#7-read-and-verify-the-html-report). |
| A PDF printed from HTML omits information you saw interactively. | Expand the relevant report sections, including nested details, and review the browser's **Print Preview** before saving to PDF again. The report workflow exports **HTML**; PDF is produced through your browser's printing feature. See [Reporting and Exporting: Read and verify the HTML report](reporting-and-export.md#7-read-and-verify-the-html-report). |
| A report or exported record contains information that should not be shared. | Review source paths, raw records, custom attributes, annotations, included source documents, optional evidence, and the technical appendix. Regenerate an appropriately scoped report and review the resulting file before distributing it. See [Reporting and Exporting: What each export captures](reporting-and-export.md#8-what-each-export-captures-and-what-to-check-before-sharing). |

**Remember:** An HTML report is self-contained and frozen at export. It can be opened offline, but it does not update when your workspace, notes, or live source changes. Generate another report for a newer handoff.

## 9. Collect useful diagnostic information

If the relevant checks do not resolve the problem, collect a small, reproducible example before changing the source or profile again. This helps distinguish unsupported input, profile configuration, source lifecycle behavior, and an application defect.

Record the following information when it is relevant:

- **Application context:** TraceScope version, operating system, current backing mode, and whether the problem also happens with the supplied sample/profile pair.
- **Exact steps:** The action you took, what you expected, and what happened instead. Note whether the problem occurs during import, after applying a filter, while following, after reopening, or during export.
- **Import evidence:** Selected importer and profile, relevant record paths or regex captures, preview summary, import diagnostics, processed/imported/skipped counts, and a few representative lines exhibiting the problem.
- **Source lifecycle:** Whether the external file was still being written, truncated, replaced, rotated, moved, or made unavailable; the original and current paths if they matter.
- **Scope and saved state:** Active source-data filters, review-only filters, comparison orientation/settings, workspace backing mode, and whether a full workspace package or standalone snapshot was saved.

To narrow down an import issue, reproduce it first with **one copied source file and one profile**. For a live-follow issue, use a disposable file or the optional deterministic [Live-Log Generator](live-log-generator.md) rather than modifying a production log. Keep a copy of the original source and any saved workspace package before testing recovery steps.

**Protect sensitive information.** Real logs, standalone snapshots, workspace packages, imported raw text, and exported reports can contain personal information, credentials, internal hostnames, source paths, or analyst notes. Remove or replace sensitive values in any reproduction material you choose to share, while preserving the structure and event order required to demonstrate the problem. Do not share a production workspace just because it contains a convenient reproduction.
